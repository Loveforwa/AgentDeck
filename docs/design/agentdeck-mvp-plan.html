AgentDeck MVP 实施计划

把设计画布里的需求拆成可以交给一个 agent 独立完成的任务，按“地基 → 白板和终端 → 工作区和 Git → 状态和网页”的顺序推进。M3 做完就是基础 MVP：能用它过完一整天真实的开发。MVP 分版本做：M0–M4 是 MVP v1；2026-10-24 第一轮验收后加了 MVP v2（M5）和 MVP v3（M6），需求在设计画布“MVP v2 · v3”那一页（画板 11、12），v2 的分波安排见下面“MVP v2 实施安排”。2026-10-25 加了插件（M7）：Auto-approve、token 用量这类以后别人也能写的功能，需求在设计画布“插件能力”那一页（画板 PL0–PL3）。2026-10-27 加了Agent 集群（M8）：按模板组一队 agent 做复杂任务，AgentDeck 里的调度器排活、守规矩，你只在关卡上出现，需求在设计画布“Agent 集群”那一页（画板 C0–C5）。

基础 MVP（P0）39 项 MVP 完整版（P1）11 项 MVP v2（M5）5 项 MVP v3（M6）9 项 插件（M7）4 项 Agent 集群（M8）10 项 里程碑 9 个 并行线 5 条

里程碑

每个里程碑结束时集成一次，按 contracts → 服务 → 界面的顺序合并。

  1. M08 项

    地基

    一个 agent 串行完成，所有接口在这一步定下来。

    完成标准pnpm dev 打开一块空白板，接假 tmux 显示一个正在回放输出的终端；故意越界的提交 CI 不通过。

  2. M113 项

    白板与终端

    能在白板上开真实的 agent 终端，关掉应用也不丢。

    完成标准同时开 6 个真实的 claude / codex，打字无可感知延迟；⌘Q 再打开，agent 一直在跑，历史输出都在。

  3. M29 项

    工作区与 Git

    每个框一个 worktree 和分支，右侧面板能提交和切分支。

    完成标准同一仓库开两个框，两个 agent 同时改代码互不影响；在面板里提交后 git log 看得到。做完这一步，就可以用 AgentDeck 开发它自己。

  4. M39 项

    状态、提醒、网页

    一眼看出谁在等你，点 dev server 链接在白板上看效果。基础 MVP 到此完成。

    完成标准agent 请求批准后 2 秒内窗口、框、顶栏一起提示，⌘J 跳过去直接回复；点 localhost 链接，页面出现在同一个框里；“10 · 全局规则”的验收场景全绿。

  5. M411 项

    MVP 完整版

    基础闭环跑通以后，再补齐需求里已经定下的增强功能。

    完成标准批准汇总、Fork 对话、关窗口后台继续、恢复上次会话、无 git 文件夹等全部可用。

  6. M55 项

    MVP v2

    第一轮验收（2026-10-24）里用起来最别扭的五件事：顶栏太占地方、窗口和框互相遮挡、状态不醒目、面板关不掉、没选中时面板没用。需求见画板 11。

    完成标准一行顶栏、红绿灯状态；窗口和框拖不到一起、拖动有对齐线；面板能收起；点空白处面板变成全白板的目录。

  7. M69 项

    MVP v3

    让 agent 通过 AgentDeck 的 MCP 在白板上开窗口、子 agent 窗口组、提交图、平移手势、工作区目录提示、面板里的 Skills · MCP，把 agent 自带的后台 agent 显示出来（N10）、左边栏的历史会话（N11）、项目框一键排版（N12）。插件入口和 cc-switch 已移到 M7。需求见画板 12–15，标“概念”的先定稿再开工。

    完成标准2026-10-25 各项形态已定（见各行）；v2 的五处缺口（IS-63–IS-67）合并后接着做。

  8. M74 项

    插件

    右键终端（或工作区框）的菜单里有一组插件项，是所有插件的入口。第一批只做两个：Auto-approve（终端底边左侧的红色小书签）和 Usage 用量记录（贴在终端上方或下方的细长条，我们自己读各 agent 的记录）。画板 12 的 N3、N4 并到这里。需求见“插件能力”页，规则见 docs/plugins.md（插件手册）。

    完成标准右键终端能开关 Auto-approve 并看到红色书签，claude、codex、omp、pi 都能自动批准；右键终端打开 Usage，终端旁边出现用量条，能拖到上方或下方。

  9. M810 项

    Agent 集群

    你选一个模板、写一句目标，AgentDeck 组一队 agent：总设计拆任务、定接口，几个实现者各在自己的 worktree 里并行做，换一家来审，合进集群分支。排活、开窗口、跑检查、守分工、等额度都是调度器（AgentDeck 里的代码，不是 agent）的事。分三期：CR0–CR6 第一期（只有 Contract-first build 一个模板，加收件箱），CR7–CR8 第二期，CR9 第三期。需求见“Agent 集群”页（C0–C5），调研 DR-64、DR-65。

    完成标准第一期：拿 AgentDeck 自己的一批任务跑一遍，你确认任务表以后不用再手动开窗口、发提示词、合分支（TC-43、TC-44）。第二期：晚上开一个集群，早上看汇报、点合并（TC-45）。

关键路径　F1 → F2 → F3 → T1 → T2 → W3 → G2 → S1 → S2 → S3 → R2。终端显示（T2）最重，越早开始越好；白板、Git、网页三条线在 M0 之后可以和它同时做。

线和线之间的接缝

两边都按 contracts 写，开发时各自用假数据，组装时直接接上。

  • 终端的 activity / silence / exit → 线 4 的状态机
  • 线 4 的 agent.turn-end → 线 3 的面板刷新
  • terminal.link（localhost）→ 线 2 在同一个框里开线 5 的网页窗口
  • workspaces.create 返回的 setup → 线 2 在框里开一个 Shell
  • 线 2 的 New terminal ▸ → 线 4 的 agents.start → 线 1 的终端窗口
  • status.changed → 线 1 标题栏、线 2 框和顶栏

规矩：并发期间 contracts 只加不改；要改就单独提交、版本号加一、其他线 rebase。详细见仓库里的 packages/contracts/AGENTS.md。

怎么用这张表

  1. 一行就是一个任务说明：复制“要做的事”“模块”“完成标准”，套进实施方案页里的任务模板，交给一个 agent。
  2. 分支名带上编号，例如 feat/T2-terminal-view，提交信息也以编号开头，方便对回这张表。
  3. 依赖没做完时用 tools/fakes 里的假实现先做，不等别人。
  4. 任务需要改 contracts 时先停下，单独提一个只改 contracts 的提交，合进 main 后其他线再 rebase。
  5. 每完成一项，跑 pnpm check 和本包测试，再请审查 agent 看一遍。
