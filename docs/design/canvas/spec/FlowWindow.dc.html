2 · 每一步存什么（图的数据，不是图片）
字段内容 from · to · kind参与者和箭头种类：call、http、ipc、event、process（起外部进程）、return、setup、check。kind 决定画法（ipc 和 event 在图上能一眼看出跨进程）。 label一句话，英文（界面文字）。解释写在 note 里，可以中文。 anchorpath、line、symbol、text（那一行里的一段原文）、commit。核对靠 text，不靠行号：行号会挪，原文在不在才说明这一步还成立。锚点层和“文档”页 D1 的代码锚点共用，格式以 D1 为准。 loop · alt这一步在哪个循环、哪个分支里（open_terminals 的 “each terminal”、“count > 6”）。 requirements哪些 TC 用例说到这一步（第三层覆盖）。 review核对结论：谁、哪一版、每步 confirmed / wrong / unsure 和证据锚点（F1）。

为什么不直接存 Mermaid：Mermaid 的 sequenceDiagram 只能给参与者挂链接（link / links 菜单），消息上不能挂（mermaid.js.org 的 sequenceDiagram 文档，2026-10-28 查）。我们要每一步都能点、能挂状态、能叠覆盖，所以真身是自己的 JSON，另外能导出 Mermaid（带 autonumber，下面附“编号 → 锚点”表），贴进 PR 和文档。
3 · 图从哪来：三种做法的实测
agent 读代码写图（带锚点）运行时录下来（trace）静态调用图（codegraph） open_terminals 实测22 步全有锚点，22/22 原文能找到；跨 3 个进程、Proxy、事件都画得出来。这次花了约 15 次读代码调用。会不会说错顺序和条件，锚点核对查不出来，要第二家核对。没做：OpenTelemetry 的 JS 自动插桩只管 http 等库，内部调用要手写 span；没找到现成的“trace → 序列图”工具。AgentDeck 三个进程加 tmux，要在几个关口自己记。508 个文件 1.6 秒建完索引。22 个锚点：5 步边全对、3 步部分对、4 步指错（例如 terminals.create 指到网页窗口的 create）、10 步没有边（HTTP、IPC、Proxy、事件、tmux 都断）。 准不准取决于 agent；锚点保证“引用的代码存在”，不保证“说法对”对跑过的那一次绝对准；没跑到的分支看不到进程内的直接调用准；同名方法会混（launch 有 8 个） 代价每张图几万 token；代码改了要再核对插桩 + 每次跑 e2e（要 tmux、假 agent）几乎为零；要用户自己装 codegraph 并在仓库里建 .codegraph/ 现成的同类Ilograph Agent Skills（2026-09-09，Apache-2.0，ilograph.yaml，每步引用代码行，/update-ilograph 更新）；Google Code Wiki（2025-11，序列图随代码重生成，链回代码）AppMap（appmap-node 包住 node / jest / vitest 录函数调用，出序列图；没提 Electron；序列图包是 Commons Clause + MIT）codegraph（tree-sitter + SQLite，MIT，就是本机这个 MCP）；infigraph 自称能从调用图出 Mermaid 序列图（页面 403，待核对） 在 AgentDeck 里的角色主路：agent 写，AgentDeck 核对第三期：在关口记录，用来核对跨进程那几步旁证：有索引就读，给核对的 agent 当候选和反证，不当真相
