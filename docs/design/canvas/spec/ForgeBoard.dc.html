Issues & PRs 窗口：放在项目主分支的框里（项目框菜单 › Issues & PRs 打开），能放大。页签 Triage · Up next · Working · My PRs · Review requests · All；行上悬停出 Work on it… / Triage / Review… / Open on GitHub。列表在窗口里不在面板里：几百行要宽表、要和分拣终端并排看，面板跟着焦点变，不适合放全局列表。 框标题上的标签：分支后面一个安静的标签 #18231 → PR #18240（GitLab 写 ! 编号），后面是 PR 的灯：CI 在跑绿、CI 失败红、有要你发的草稿黄（算进 “n waiting”）、合并后写 ✓ merged。单击标签打开面板的 PULL REQUEST 一节；聚焦这个框时画一条 1px 墨色虚线到列表里那一行（和 S1 的父子关系线同一种画法）。 面板的 PULL REQUEST 一节：只管聚焦的这个工作区的 PR，放在分支和提交框之间。失败的检查能 Send log to agent、Re-run…；review 线程勾几条 Send to agent；草稿在这里只列出来，统一在收件箱发；Merge… 照仓库规则，不满足时灰掉写原因。刷新时机照 ScmPanel 原来的规矩，另加：CI 跑着时每 60 秒、同步到新线程时。

规则怎么做 排序代码算分、能看 Why：紧急标签（security、regression、crash、P0，项目设置能改）+30；10 × log2(1 + 反应数 + 评论人数)；7 天内有动静 +10；help wanted / good first issue +5（你是贡献者 +15）；已有开着的关联 PR −20；needs-info −15；指派给别人的默认不显示。agent 的优先级建议不进分数。 同时几个项目设置 Issue slots，默认 3、最多 8。Work on it、Review 各占一个；分拣终端另算（一个项目同时一个）；从 issue 开的集群占 1 个。满了进 Up next 排队（你在排，所以排队；不像自由模式里 Lead 开子 session 超了直接拒绝）。 背压这个项目待你发的草稿 ≥ 6 条时不自动开下一个：瓶颈是你看草稿的速度，agent 再多也只是堆草稿。 额度开下一个之前看 LimitService（PL5）里这个账号是不是 limited；设了 Fallback agent 就用它开。跑到一半撞额度：普通 issue 终端归 Auto-resume（PL4），集群里的归 CR8，要换家用 Hand off to ▸（SE6）。 同步首次只拉最近更新的 500 条，之后按更新时间增量、窗口开着时 5 分钟一次；只轮询挂在工作区上的 PR 的 CI（60 秒，跑完就停）；限额剩 10% 时暂停自动同步。
