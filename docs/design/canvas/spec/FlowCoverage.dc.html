2026-10-28 按推荐先定，待你确认

“覆盖”在这里说的是三件不同的事，问的人、算的人、出错的后果都不一样。三层都叠在同一张图上，所以图本身先得对：先做第一层（图对不对、漏了什么），它就是你说的“由子 agent 判断”；第二层机器就能算，紧跟着做；第三层要人确认对应关系，最后做。

1 · 三种覆盖分别是什么
① 图覆盖代码（Review）② 测试覆盖图（Tests）③ 需求覆盖图（Requirements） 问的是图上每一步说得对不对？这条流程里有哪些分支、出错的路、副作用图上没画？图上哪几步被单元测试或 e2e 真的跑到了？跑到的时候下游是不是假的？哪些 TC 用例说到了哪几步？哪几步没有任何用例管？ 谁来判断核对的子 session（Verifier），默认换一家：claude 画的 codex 核，反过来也一样机器：V8 覆盖数据按锚点行叠上去。子 agent 只判断“跑到了有没有断言”agent 按 TC 的步骤和预期提一版对应，你确认；e2e 用例按 tcXX 命名的自动对上 输入图、锚点核对结果、锚点附近的代码、codegraph 给的候选（这一步所在函数还调了谁、有哪些 throw / catch / if）vitest 的 coverage-v8 JSON；e2e 时主进程、utility 进程的 NODE_V8_COVERAGE，界面进程的 Chromium 覆盖（待核对）docs/status/tracking.py 的 TC（步骤、预期、状态）、e2e/tests 的文件名 每一步的结果 Confirmed · Unsure · Wrong；漏掉的画成虚线幽灵箭头，标 main path / error path / side effect Run · Run fakes · Not run · Not loaded（这次测试根本没加载这个文件）TC 小签：TC-34 · Verified / TC-46 · Not built；一步没有签就是没人管 怎么核查每条结论必须带证据锚点，机器先核证据的原文在不在，不在就作废；你逐条 Accept / Reject，或点开编辑器自己看数字可复现：Run tests for this flow 只跑相关的测试文件，覆盖数据存下来，谁都能重算对应关系存在图的 requirements 里，进 PR 让人审；TC 的状态以 tracking.py 为准 代价一次核对几万到十几万 token（待实测）；只重核改过的步骤要给仓库装 @vitest/coverage-v8（现在没装、没配）；e2e 覆盖要实验维护对应关系；TC 改了要重看 先后第一期第一期（单元测试）；e2e 第三期第二期
