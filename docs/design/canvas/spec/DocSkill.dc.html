一个专门写文档的 skill，AgentDeck 自带，五家 agent 都能用。它管三件事：先说结论的短句；不写套话；每句讲代码的话后面跟着从仓库根写起的 path:行 和符号，写完自己跑一遍 agentdeck doc check。全文草稿在 p11/drafts/agentdeck-docs-SKILL.md（英文正文，另有一节中文写作规则）。

1 · 怎么带给 agent
事项做法 放在哪AgentDeck 自带的 skill，和现在的 agentdeck skill 一样由 packages/agent-adapters/src/skills/library.ts:255 builtinSkillFiles 写进数据目录，按 N9 的办法带进终端（claude、omp 用 --plugin-dir，pi 用 --skill，kimi 用 --skills-dir；codex 带不进，靠提示词指路）。不写用户自己的 skill 目录。 每轮多少 token描述 191 个字符，约 47 token，勾上的终端每轮常驻；正文约 8.9k 字符（UTF-8 字节数 / 4 约 2.5k，偏高），只有用到时才读。 默认勾不勾默认不勾（不让每个终端都付描述的钱）。AgentDeck 为文档开的终端自动勾上：New doc… 里的 “Ask a new claude to draft it”、Verify claims 的核查终端。按 K0 的三层启用：可以在项目里设成默认勾上（写文档多的项目）。 没勾的终端从文档窗口发出去的提示词（Ask…、Send comments）第一次会带一句 “Before editing, read <数据目录>/skills/agentdeck-docs/SKILL.md”，五家都能直接读文件，不用重启终端。同一个终端只带一次。 和项目自己的规矩skill 第一条就是：仓库里有 AGENTS.md、CLAUDE.md、CONTRIBUTING.md 的写作规矩时，它们优先。本项目的规矩（界面字用英文、注释和文档可以中文、编号规则）照旧。
2 · 三条规矩
用人话每节第一句是结论，理由在后面。一句只说一件事；主语是具体的东西：文件、函数、按钮上的字、数字。数字写怎么量的、在什么上量的、哪天量的；没量的写“没量过”。不知道的写“待核对”，不拿一句听着对的话盖过去。真有先后才用编号；列表是并列的东西，不拿列表写论证。
少 AI 味不写：赋能、抓手、闭环、打通、无缝、强大的、一站式、极致；值得注意的是、总的来说、综上所述、不难看出。英文同理：robust、seamless、leverage、delve、crucial、In summary。不用排比凑节奏，不写“不仅……而且……更……”，不自问自答，不收尾总结。不满篇加粗、不用感叹号、不用 emoji，破折号少用。参考：维基百科 WikiProject AI Cleanup 的 “Signs of AI writing”（指南本身说这些只是弱信号，要几种一起出现才算）；本仓库 AGENTS.md 的文风。
引用要密“现状”“怎么工作”“改了什么”这几节，每段至少一处引用；讲代码的每条列表项各带一处。从仓库根写全路径；范围尽量窄（30 行以内）；后面跟符号。说“定义成什么”指定义，说“谁调了它”指调用处，说“测过了”指测试。计划中的文件标 (new)；别的仓库写来源、版本和日期；实验钉住版本 path@提交:行。没打开过的文件不许引。写完跑 agentdeck doc check，not found 和短路径必须修掉。
3 · 改写前后（同一件事：终端里的文件链接）
改写前 终端链接处理是 AgentDeck 中一个至关重要的功能模块。值得注意的是，该模块不仅能够智能识别各种格式的文件路径，而且还能无缝对接用户的编辑器，从而极大地提升了开发效率。在实现层面，系统采用了正则表达式进行匹配，并通过统一的接口调用外部程序。总的来说，这一设计充分体现了以用户为中心的理念。 问题：一处引用都没有，没法核查；“各种格式”“极大提升”说不出依据；“正则表达式”“统一的接口”是哪个、在哪；最后一句什么也没说。红线是 skill 第 3、4 节点名的写法。
改写后 终端输出里的 文件:行号 由 findLinkMatches 认出来（packages/ui/widgets/terminal/src/links.ts:33）。它认三种写法：a.ts:12:3、tsc 的 a.ts(12,3)、Python 的 File "a.py", line 3（同一文件 :14-17）。 单击以后交给 app.openInEditor（packages/ui/widgets/terminal/src/TerminalWindow.tsx:243-247），用设置里的 editorCommand 打开到那一行，默认是 code -g（apps/desktop/src/main/settings.ts:12）。找不到编辑器时退回系统的默认程序（apps/desktop/src/main/app-service.ts:123-134）。 这套规则在 packages/port-watch/src/links.ts 里还有一份副本，因为界面包不能 import 服务包；改的时候两边一起改。 每句都能点开核对（2026-10-28 对着 871dd81 逐条看过）。没有形容词，没有总结句；读完就知道去哪改。
4 · 四类文档的提纲（New doc… 的模板也用这几个）
需求 Requirements技术 Design实现 Implementation实验 Experiment 问题：谁、什么时候碰到，一个具体例子现状：现在的代码怎么做的（每段都有引用）改了什么、为什么：每处改动一小节，引用新代码和测试问题：想知道什么 用户看到什么：一步一步，界面原文用英文决策：每个决策写选项、推荐、理由、代价、要不要你拍板怎么测的：命令和结果怎么做的：版本、提交、机器、原样的命令，别人能重跑 规则和边界情况；不做的接口：类型和调用，写在哪个文件还没做的、已知的缺口结果：原始数字的表，再说它说明了什么 验收：能照着测的用例（前提、步骤、界面、后台），对上 TC 编号风险和不确定的（待核对）后续：带编号的任务和问题结论：现在知道了什么、还不知道什么；脚本和数据在哪
和本项目已有的格式一致：技术文档的“决策”就是调研记录（DR）的 assumed / found / decision / pros / cons；需求的“验收”就是 TC 用例的写法。
5 · 交出去之前自查
  1. 每个路径都在这个 worktree 里，或者标了 (new)、外部来源、钉住的版本。跑 agentdeck doc check；不在 AgentDeck 里时用 ls 和 sed -n 逐个看。
  2. 每句讲代码的话和它引的几行放在一起再读一遍：那几行证明不了这句话，就改话或改引用。
  3. 按第 2 节的词表搜一遍，删掉；删掉读者本来就知道的段落。
  4. 在终端里用一两句话说写了什么、还有什么待核对；不把文档贴进对话。
  5. 按评论改时只改评论挂着的那段，用 agentdeck doc reply 逐条回复，不替你 Resolve。
