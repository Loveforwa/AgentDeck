A产品形态

画原型时，和最初想象不一样的地方

A1

agent 的对话是在白板上的真终端里，不是我们自己画的界面

已解决
原来以为

在 AgentDeck 自己的面板里渲染每个 agent 的对话，统一样式。

实际情况

每家 agent（claude、codex、gemini）都有自己的 TUI，功能和快捷键一直在变；自己重画等于给每家重做一遍界面，永远追不上。

决策

白板上直接放真实的终端，agent 在里面原样运行；AgentDeck 只管窗口、工作区、状态和 Git。

好处

不用适配每家界面，agent 升级我们不用跟；用户在里面的操作和平时一模一样。

代价

没法统一对话的样式；“谁在等你”这类信息只能从外面推断（见 C5、E3）。

出处：设计画布 v2 原型；实施方案「技术选型」

A2

不要左侧栏，也不要每个框上的 +/− 改动数

已解决
原来以为

左侧栏放会话列表；每个工作区框右上角显示增删行数。

实际情况

白板本身就能看全局，左侧栏重复且占地方；改动数在框上没有可操作的东西，只是噪音。

决策

去掉左侧栏，操作都走右键和触控板；改动只在右侧源代码管理面板里看。

好处

白板面积大，界面更安静，更接近“工具”而不是“AI 产品”。

代价

新用户不知道右键能做什么，需要空白状态里给提示按钮。

出处：原型评论 fb33f60b

A3

界面全英文，文档用中文

已解决
原来以为

界面文案用中文。

实际情况

产品以后面向的用户和生态都是英文的，界面文字和 agent 输出也是英文。

决策

产品界面上出现的所有文字一律英文；需求说明、注释、文档、提交说明里的解释用中文。

好处

界面和 agent 输出、命令行一致；以后不用整体翻译一次。

代价

需求画板里中英混排，读的时候要分清哪些是界面原文。

出处：评论 9fb04e3d；根目录 AGENTS.md

B技术方案

定技术选型时推翻的设想

B1

终端进程交给 tmux，AgentDeck 只负责显示

进行中
原来以为

用 node-pty 在应用里直接起 agent 进程，xterm.js 显示。

实际情况

进程跟着应用走：关掉应用 agent 就没了；看不见的终端也要一直收输出，开多了会卡；重启后的历史要自己存。

决策

所有 agent 跑在 AgentDeck 自己的 tmux 实例（tmux -L agentdeck）里；只为视口里的终端 attach 显示，移出就断开；摘要、链接、活动状态都向 tmux 要。

好处

关掉应用 agent 继续跑，重开直接接上；开很多终端也不卡；用户能在自己的终端里 tmux attach 接上同一个会话。

代价

多了一层 tmux，按键、滚动、颜色都要调（见 E2、E4）；要求用户装 tmux（见 E5）；Windows 没有原生 tmux。

出处：实施方案「技术选型」「风险 4」；F7 试验

B2

Git 不监听文件，只在三个时机刷新

已解决
原来以为

监听每个 worktree 的文件变化，实时刷新源代码管理面板。

实际情况

每个 worktree 都要一个监听器，大仓库开销大；agent 在一轮里会连续改很多文件，实时刷新没意义。

决策

只在切换聚焦、agent 一轮结束（钩子通知）、自己做完 git 操作时刷新，另有手动刷新按钮。

好处

少一个模块；多开工作区没有额外开销；空闲时 CPU 接近 0。

代价

在外部编辑器里改的文件，要等下次聚焦或手动刷新才显示。

出处：实施方案「git 刷新时机」；contracts git.ts

B3

白板不靠整体缩放放下更多窗口，而是拖小窗口、变摘要卡

已解决
原来以为

双指捏合缩放整块白板，缩小了就能看到所有终端。

实际情况

xterm 用 canvas 画字，被 CSS 缩放后会糊，鼠标选区也会错位。

决策

去掉双指捏合；靠拖边框把窗口改小，小于 320×200 时变成摘要卡（tmux capture-pane 取最后 3 行）；⌘ + 滚轮缩放只留作备用，低于 75% 同样变摘要卡。

好处

真终端永远按 1:1 渲染，字清楚、选区准；摘要卡不用接上终端，不占资源。

代价

不能像地图那样随手缩小看全部；摘要卡只有几行，看细节要点开。

出处：评论 4b8282c6；实施方案「风险 1」

B4

状态靠 agent 自己的钩子，不靠识别屏幕文字

进行中
原来以为

用正则匹配终端输出，判断 agent 是在跑、在等批准还是说完了。

实际情况

各家 TUI 一改版正则就失效；看不见的终端没有接上显示，也拿不到屏幕。

决策

claude 用 hooks（启动时 --settings 临时注入），新版 codex 也用 hooks（本机 0.159 已有 PermissionRequest、Stop）；其他 agent 只用 tmux 的输出活动判断运行中和空闲，可选配一句“等你”的文字。

好处

claude、codex 的状态准确，看不见的终端也准；不受界面改版影响。

代价

依赖各家钩子的格式，升级可能变（检测到变了就退回 tmux 活动）；没有钩子的 agent 不会进入“等你”。

出处：评论 d101822a；「6 · 终端状态与提醒」状态来源表；线 4

C需求细节

在设计画布上评论、逐条改需求时改掉的做法

C1

运行中的终端换不了目录，拖进别的框只能新开或 Fork

进行中
原来以为

把终端拖进另一个工作区框，它就切到那个框的目录。

实际情况

进程启动后工作目录就固定了，外面改不了。界面上看起来换了，实际还在旧目录里改文件，右侧 Git 面板就对不上。

决策

终端创建时绑定它所在的框；拖进别的框会弹回原处，询问 New conversation（空白新开）或 Fork conversation（claude --resume <id> --fork-session、codex fork <id>，带着对话去新目录）。

好处

Git 面板显示的永远是 agent 真正在改的目录；Fork 让对话能带过去。

代价

多一步确认；Fork 带过去的只是对话，旧目录没提交的改动不会跟过去；claude 跨目录 fork 还要实测（见 F3）。

出处：评论 91112625；「5 · 终端窗口」

C2

添加项目不用从访达拖，改成固定入口

已解决
原来以为

把文件夹从访达拖到白板上就添加成项目。

实际情况

拖拽入口难发现，也容易误操作。

决策

右键 › Add project…、顶栏 Projects ▾ › Add project…、新建工作区对话框里的项目下拉，三处打开同一个选文件夹窗口。

好处

入口固定好找；添加完直接进入新建工作区。

代价

比拖拽多点一下。

出处：评论 a650ccd5；「2 · 项目」

C3

项目不一定是 git 仓库，也可以是多个仓库

进行中
原来以为

每个项目就是一个 git 仓库，每个工作区就是一个 worktree + 分支。

实际情况

有的文件夹没有 git（笔记、脚本）；有的项目是一个文件夹下几个仓库（web、api），要同时改。

决策

项目分三种：单仓库、多仓库（每个工作区给选中的仓库各建一个同名分支的 worktree，agent 在父目录跑）、普通文件夹（只有主目录工作区，面板提示 Initialize Repository）。

好处

覆盖实际的项目形态；没有 git 的文件夹也能用。

代价

多仓库的提交、切分支、失败回滚都要按仓库各做一遍，复杂度明显上升，所以多仓库推迟到 MVP 之后；普通文件夹没有分支隔离，两个 agent 会互相影响。

出处：评论 de119763、44b1007a、1447b3d2；contracts project.ts

C4

“主力”是用户起的名字，应用不判断

已解决
原来以为

（需求图里写着 lead，看起来像应用能识别谁是主力 agent。）

实际情况

应用没有依据判断谁是主力。

决策

lead 只是用 Rename 起的名字；没改名时标题栏只显示 agent 名。

好处

不做猜测，不会错。

代价

用户要自己改名才能区分同类 agent。

出处：评论 d101822a

C5

“等你回复”的定义收窄

已解决
原来以为

agent 停下来就是在等你。

实际情况

agent 每一轮说完都会停下，大部分时候只是做完了，不是在问你。全都标橙会让提醒失去意义。

决策

只有 agent 用自己的提问工具（如 claude 的 AskUserQuestion）才算“Needs reply”；一轮说完算 Idle；需要批准算“Needs approval”。

好处

橙色提醒少而准。

代价

agent 用普通文字提问时不会变橙，要自己看。

出处：「6 · 终端状态与提醒」

C6

“全部选 yes”改成先列清单的 Approve all

推迟
原来以为

检测到任何窗口弹出 yes/no 确认，就自动全部选 yes。

实际情况

有的确认是危险命令（rm -rf、强推、清数据库）；一点就全批，出了事查不到。

决策

Approve all（⌘⇧J）先列出每条请求要做什么，破坏性命令默认不勾，只选“允许一次”；另有按工作区开的 Auto-approve，默认关，危险命令照样停下，每次留记录。提问和多选永远留给用户。

好处

省掉一个个点 y 的麻烦，又不会误批危险操作。

代价

多一次确认；手动 Approve all 是给终端发按键，依赖各家确认界面的按键（待线 1 核对）。属于 P1。

出处：评论 ed7b7930；「6 · 终端状态与提醒」

C7

“关闭”分三种，重开能接回原来的对话

推迟
原来以为

关掉应用就是退出。

实际情况

用户有时只想让窗口消失、agent 继续跑；有时想彻底停掉；电脑重启后还想接着原来的对话。

决策

Close window（后台继续、照常通知）、Quit（应用退出，agent 在 tmux 里继续）、Stop all and quit（全部结束）。全部停止或重启后，Restore all 按记下的会话 id 精确接回（claude --resume <id>、codex resume <id>），Shell 在原目录填好命令不运行。

好处

三种需求都能满足；同一目录两个 claude 也不会接错对话。

代价

要为每个终端记录启动命令和会话 id；后台常驻占一点内存。属于 P1。

出处：评论 246224d2；「9 · 保存与重启」

D接口与并发

先定接口再并发开发，过程中发现的问题

D1

先定接口再并发，接口第一版不够用

已解决
原来以为

contracts 0.1.0 写完，各条线照着做就行。

实际情况

写假实现时发现 10 处不够或说得不清：没法恢复 stash、没法删分支（回滚会留下分支）、改了基础分支 status 拿不到、开 agent 不带终端大小（首屏会跳）、删除有改动的工作区没法“确认后强删”、kill 后发不发 exit、attach 后先不先给整屏等。

决策

在各线开工前出 0.1.1，全部只加不改；BranchChoice.from 放宽为可选（不填时每个仓库用自己的基础分支）；kill 后发 terminal.exit（128 + 信号）。

好处

问题在写真实实现之前就暴露并统一了，5 条线不会各猜各的。

代价

多一次版本号和假实现返工；以后各线还会发现新的，需要有人收集合并。

出处：提交 b24a0ca；tools/fakes/CONTRACT_NOTES.md

D2

窗口组件的 props 漏在接口外面

已解决
原来以为

白板、终端、网页各做各的，组装时再对。

实际情况

终端（线 1）和网页（线 5）是放进白板（线 2）里的窗口，三条线同时开发，如果不先定“白板给窗口什么”，每条线都会自己发明一套。

决策

contracts 0.1.2 加 WindowComponentProps：所在工作区、聚焦、内容区大小、摘要卡、可见性，以及 updateData、setStatus、openWindow 等回调；线 2 先单独提交注册表。

好处

三条线并发不用等彼此。

代价

接口里多了一块 UI 相关的约定，以后改它要三条线一起配合。

出处：提交 120559a

D3

每次合并 pnpm-lock.yaml 都冲突

已解决
原来以为

各条线只改自己的目录，合并不会冲突。

实际情况

几乎每条线都加依赖，锁文件是全仓库共用的一个文件。

决策

合并时先取 main 的锁文件，再 pnpm install 重新生成，最后用 --frozen-lockfile 确认一致。

好处

不用人工比对锁文件；结果和直接安装一致。

代价

每次合并多一步；两条线加了同一个依赖的不同版本时要人工选。

出处：第 1 波合并（cbecb00…f3ba92e）

D4

检查规则比部分代码晚到

已解决
原来以为

第 1 波各包同时开始，CI 规则和代码一起合进来就行。

实际情况

F6 先写完，F5 的 lint 规则后到，合并后才发现 import type 不合规；F4 的 vite.config.ts 用了 node 内置模块，被“界面不能用 node 模块”的规则误伤；ESLint 还扫到了并行 session 的 worktree 目录。

决策

合并后统一修：eslint --fix；边界规则放过构建配置文件并加样例；ESLint 和 .gitignore 忽略 .claude/worktrees。

好处

规则和代码在 main 上一致，之后的线一开始就受约束。

代价

第 1 波合并时多了一次修补提交。教训：检查规则最好在第 0 波就合进去。

出处：提交 77e8373、2ce7166

D5

并行开发需要正式的仓库目录

已解决
原来以为

在临时目录里先写，后面再说。

实际情况

并行 session 要各自的 git worktree，临时目录没有 git，而且会被清理。

决策

移到 /Users/liu/2026/agenduck，git init，第一次提交后再开第 1 波。

好处

每条线一个分支，互不干扰，能逐个检查、合并。

代价

代码还没推到 GitHub，CI 没在云端跑过（见 E7）。

出处：提交 86afd45

D6

第 2 波又收到约 30 条接口意见

进行中
原来以为

0.1.1 和 0.1.2 之后接口够用了。

实际情况

E3

从程序坞打开的应用拿不到 shell 里的环境

进行中
原来以为

应用里起的 agent 和在终端里敲命令一样能找到、能登录。

实际情况

macOS 从程序坞打开的应用环境很少：PATH 里没有 /opt/homebrew/bin、~/.local/bin，可能缺登录相关的变量。tmux 服务也只认第一次启动它的进程的环境（F7 发现在 Claude Code 里起服务会把 CLAUDECODE=1 带给所有会话）。F7 当时看到的 403 后来查明是试验环境里 claude 没登录。

决策

好处

代价

启动多一次 shell（几百毫秒）；用户 shell 配置有问题（卡住、报错）时要兜底；tmux 服务要用干净的环境启动，不能继承 Electron 的。

E15

打包后嵌入的 localhost 页面算跨站，登录 cookie 存不进

已解决
原来以为

（风险 3）iframe 里的本地页面可能丢登录态，开发模式下试一下就知道。

实际情况

开发模式下白板也是 http://localhost，和页面同站，看不出问题；打包后白板是 file://，iframe 里的 localhost 算跨站，SameSite=Lax 的 cookie 根本存不进（线 5 实测）。

决策

主进程把本地来源响应里的 Set-Cookie 改成 SameSite=None; Secure，服务端写的登录 cookie 就能用；页面 JS 写的 cookie、第三方 OAuth、弹窗在 MVP 里用 Open in browser；P1 用 <webview partition> 独立窗口模式（实测全部能登录，也能跟着白板缩放）。

好处

大部分本地开发服务的登录直接能用。

代价

改写 cookie 只对本地来源，别的情况要用户点 Open in browser；每个 session 的 onHeadersReceived 只能挂一个，别的模块要改响应头得合并。

出处：packages/ui/widgets/browser/AGENTS.md
